# ドキュメントコメント規約

本ドキュメントは、Aquavit VR のソースコードに記述する XML ドキュメントコメントの規約です。[FloatSoda の DocumentationComments](https://github.com/sumx21t-3310/FloatSoda/blob/main/docs/DocumentationComments.md) を土台にしています。

ドキュメントコメントは、正式な API Reference の原稿として扱います。目的は、IDE や API Reference 上で、API の役割・契約・副作用を確認できるようにすることです。チュートリアル・設計背景・概念解説・実践的な使用例は、原則として API Reference には含めず、`docs/` に記載します。

## 1. 適用範囲

アクセス修飾子にかかわらず、原則としてすべての型とメンバーにドキュメントコメントを記述します。対象は次の要素です。

- クラス
- 構造体
- レコード
- インターフェース
- 列挙型
- デリゲート
- コンストラクター
- メソッド
- プロパティ
- フィールド
- イベント
- 演算子
- 型パラメーター
- 列挙値

役割や契約が存在する場合は、アクセス修飾子(`public` / `protected` / `internal` / `private`)を問わず記述します。内部 API や非公開メンバーのコメントも、フレームワークの保守・コードレビュー・デバッグ・API 変更に必要な内部向け API Reference として扱います。

ただし、次の要素は省略できます。

- コンパイラーまたはコード生成によって生成される要素
- 意味や契約を持たない単純なバッキングフィールド
- 自明な定数の内部保持のみを目的とするフィールド
- ドキュメントコメントを継承し、追加または変更された契約がないオーバーライド
- 一時的なローカル実装に限定され、独立した役割を持たない要素
- `tests/` のテストクラスとテストメソッド。テストの仕様は、メソッド名で表します(→ [CONTRIBUTING.md](../CONTRIBUTING.md) の「テストの命名」)
- `samples/` の top-level statements

省略できるか迷う場合は記述します。

### ビルドでの検査

規約の一部は、ビルド時にアナライザーが検査します。検査されない項目は、レビューで確認します(→ [REVIEW.md](../REVIEW.md))。

| 検査する内容 | ルール | 対象 |
|---|---|---|
| `public` な型とメンバーにコメントがあること | `CS1591` | `src/` |
| `<param>`、`<typeparam>`、`<returns>` の過不足と、内容が空でないこと | StyleCop の `SA16xx` | すべてのプロジェクト |

英語の定型文を求めるルール(`SA1623`、`SA1642` など)と、文末のピリオドを求めるルール(`SA1629`)は、日本語で記述するため対象外とします。設定と理由は [.editorconfig](../.editorconfig) にあります。

## 2. 基本方針

ドキュメントコメントには、API Reference として必要な情報を記載します。

- `<summary>` には、その API が何を行うかを簡潔に記述すること。
- メソッドとコンストラクターの引数は、`<param>` を使用して省略せず説明すること。
- 型パラメーターがある場合は、`<typeparam>` を使用して役割や制約を説明すること。
- 戻り値がある場合は、`<returns>` を使用して戻り値の意味を説明すること。
- プロパティの値に補足が必要な場合は、`<value>` を使用して意味や制約を説明すること。
- 例外を送出する場合は、`<exception>` を使用して発生条件を記述すること。
- 単位・値の範囲・`null` の可否・既定値・失敗時の挙動など、API の使用に必要な契約を明記すること。
- 状態変更・再計算・再描画など、観測可能な副作用を明記すること。
- 要約・引数・戻り値だけでは不足する契約上の補足には `<remarks>` を使用すること。
- 長い使用例・チュートリアル・設計意図・内部構造の解説は `docs/` に記載すること。
- `<example>` は原則として使用しないこと。API Reference 上で確認する必要性が高い短い例に限り使用できる。

## 3. API Reference と docs の責務

ドキュメントコメント(API Reference)には、次の内容を記載します。

- API の役割
- 引数と型パラメーターの意味
- 戻り値の意味
- プロパティ値の意味
- 発生する例外と条件
- 値の単位や有効範囲
- `null` の可否
- 既定値
- 副作用
- 変更が伝播する範囲
- 再実行される処理
- 失敗時の挙動
- 密接に関連する API
- Web 標準の API に対応する場合は、対応する仕様の名前(例: DOM Standard の `Node.appendChild`)

`docs/` には、次の内容を記載します。

- チュートリアル
- API の具体的な使い方
- 複数 API を組み合わせた例
- DOM・Style・Layout・Paint の概念解説
- Web 標準との対応関係と、対象範囲
- 設計意図
- 内部構造
- よくある間違い
- 実践的なサンプル
- 処理の流れ全体の解説

ドキュメントコメントで「何であるか」「どのような契約か」「副作用は何か」を説明し、`docs/` で「どのように使うか」を説明します。

## 4. 引数、戻り値および型パラメーター

すべての引数に `<param>` を記述します。引数名や型を言い換えるだけの説明を避け、意味・単位・有効範囲・`null` の可否・所有権・ライフタイム・副作用を記載します。

```csharp
/// <param name="width">
/// 描画先の幅。単位はピクセルで、0より大きい値を指定します。
/// </param>
```

型パラメーターには、その型が担う役割と必要な制約を記載します。

```csharp
/// <typeparam name="TNode">
/// 走査の対象にするノードの型。
/// </typeparam>
```

戻り値がある場合は、`<returns>` に成功時・失敗時・対象が存在しない場合など、それぞれの値が表す意味を記載します。

```csharp
/// <returns>
/// イベントが処理された場合は <see langword="true"/>。
/// 処理対象が存在しない場合は <see langword="false"/>。
/// </returns>
```

## 5. 再計算を引き起こす変更

Style、Layout、Paint の再計算を引き起こす変更は、後続の処理に影響するため、副作用として扱います。どの段階の再計算が必要になるかを明示します。

必要に応じて、次の情報を記載します。

- 直接必要になる再計算(Style / Layout / Paint)
- 間接的に必要になる再計算
- 変更が伝播する関連オブジェクト
- 伝播が停止する境界
- 値が変化しなかった場合の挙動

実装メソッド名だけでなく、結果として何が起きるかを説明します。「内部のメソッドを呼び出します」という説明では、利用者は何が再計算されるのかを判断できません。「この要素と子孫の Layout を、次のフレームで再計算します」のように、結果を書きます。

継承元の挙動を派生型で変更しない場合は、説明を繰り返しません。派生型で再計算の種類や伝播する範囲を変更する場合は、その差分を明示します。

> **実装状況** — 再計算の要否を管理する仕組みは、Phase 2 の [#17](https://github.com/sumx21t-3310/Aquavit-VR/issues/17) で実装します。状態の名前と書き方の例は、実装時にこの章へ追加します。

## 6. 関連型への参照

意味の上で関係する API は、相互に参照できるようにします。次の関係を参照対象とします。

- 密接に関連する API
- 代替となる API
- 対になる API(追加と削除、登録と解除など)
- 処理の前後の段階で対応する型(DOM のノードと、そのノードから生成される Layout の型など)

参照には、必要に応じて `<see>` または `<seealso>` を使用します。

## 7. 参照しないもの

次の要素には、原則として明示的なリンクを追加しません。

- 継承元の型
- 実装しているインターフェース
- 型階層から自動的に判別できる型
- 同じ名前空間に属するだけの型
- 関係が薄い型

継承やインターフェースの実装関係は、IDE や生成ツールに委ねます。ドキュメントコメントでは、型階層だけでは表現できない意味上の関係を補足します。

## 8. 継承およびオーバーライド

基底メンバーと契約が同じで追加の説明がない場合は、`<inheritdoc/>` を使用できます。

```csharp
/// <inheritdoc/>
public override ILayer Clone()
{
    // ...
}
```

ただし、次に該当する場合は `<inheritdoc/>` に頼らず、変更した契約を明示します。

- 振る舞いを追加または変更する
- 例外条件を追加する
- 再計算の種類や伝播する範囲を変更する
- 副作用を追加する
- 戻り値や `null` の扱いを変更する
- スレッド・所有権・ライフタイムに関する制約を追加する

## 9. 記述言語

XML ドキュメントコメント(`/// <summary>`)は**日本語のみ**で書きます。1つのソースに2言語を併記しません。これは、日本語を既定の言語とする FloatSoda の方針を引き継いだものです。

Web 標準の用語、API の名前、識別子は、英語のまま書きます(`Element`、`computed style`、`flex container` など)。

## 10. 入力語彙

入力デバイスを指す場合、「マウス」単独ではなく「ポインター」と記述します。VR のレーザーポインターとマウスの両方が入力になるためです。DOM のイベント名は、Web 標準のとおり `pointerdown` や `click` と書きます。

## 11. 原則

Aquavit VR のドキュメントコメントは、補助的な実装コメントではなく、正式な API Reference を構成する情報です。

- 公開 API に限らず、原則としてすべての型とメンバーに記述すること。
- API の役割・引数・型パラメーター・戻り値・例外・制約・副作用は、ドキュメントコメント内で完結させること。
- 長い説明・学習用途の内容・設計背景・実践的な使用例を含めず、`docs/` へ分離すること。
- 型階層はツールに任せ、意味上の関係と観測可能な副作用をコメントで補足すること。
